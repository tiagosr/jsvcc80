Findings
========

Findings about the agent orchestration experiment.

## Philosophical findings
- An interesting angle: agentic coding with LLMs is a version of high-level programming that's quite close to the ideal of languages like Lisp, in intention - a language that encompasses both high-level abstraction and fundamental data structure manipulation. Though LLMs lack severely on repeatability - and are not able to land repeatable results without *a lot* of iterations, and Lisp came from a first-principles approach, whereas an LLM as a programming language analogue would have come from whatever could have been considered the exact opposite of first-principles, as they embed **every single principle** and try to see what sticks.
- One thought that came to me during this process: agentic coding sounds like the weird manifestation of [INTERCAL](https://esolangs.org/wiki/INTERCAL). Prompt/agent/skill engineering is basically the `DO`, `PLEASE`, `PLEASE DO`, `MAYBE`, `DON'T`, `DO NOT`, `PLEASE DON'T`, `PLEASE DO NOT` and `PLEASEN'T` directives *including* the "politesse" check - and checklists and hard gates are basically the `COME FROM` operator (as INTERCAL doesn't have GOTO, as it is considered harmful). `FORGET`, `ABSTAIN`, `IGNORE`, `REINSTATE` and `REMEMBER` were all there in INTERCAL, since 1972.

## Software design issues
- There seems to be a sweet-spot of capability/overbearingness in the models about what kinds of tasks an LLM (local or frontier) takes on before they either start creating "laziness" - especially with delegating implementation decisions to the LLM, allowing the implementation and the quality of the output to drift away from control - or "babysitting" - especially with monitoring the thought processes to see where a model might drift away from the spec towards a dead end or a poorly-defined direction. The sweet-spot seems to be on the range of 15B to 50B parameters - more and it invites laziness, less and it invites babysitting
- In fact, "babysitting" might be a better range to operate a coding LLM through than "laziness" - although the process and outcome of the babysitting range actually hinges on the user's own capabilities in defining the tasks that the models will take on. An experienced software developer, capable of scoping and architecture work, is able to drive an LLM to higher-quality output and less iteration cycles than a person with less experience on scoping, and runs a smaller risk of mental overload while monitoring the LLM's output.
- Unbounded tasks, as in human-developed software, generate output filled with assumptions - and most of the time with LLMs, these assumptions are in the direction of the quickest-shipping output. If a task cannot be explained without unexpected assumptions, expect the task to diverge from the original plan. This project in particular has some assumptions that are well-registered facts (the architecture of the Z80 is 50 years old as of Jul 2026, and C is just a few years older than that, there are potentially enough facts on an LLM's parameters to convey a lot of it without issues), but for other tasks there could be less or incomplete or misleading assumptions.
- Tendencies:
  - There is a subtle underlying "not invented here" tendency on an LLM's operation, even between parts of the same project. It is a constant monitoring effort to not let multiple implementations of the same thing to pop up in the project, necessitating manual intervention, and tools like `graphify` actually managed to bring the occurrence of that down significantly. It won't be a junior dev's usual setup, though.

## Context scale issues
- Some models have a proclivity to generate large classes, increasing the file sizes and increasing the chances of issues with future sessions. Directives to reduce the file sizes (limit functions per file, limit function sizes) need to be better defined - another case of preferentially not trusting the model's judgement on that.

## Tooling issues
- Some combinations of "harness + AGENTS.md + inference engine + model" can trigger incredibly weird inference loops - in particular `Qwen 3.6 27B` and `Qwen 3.6 35B A3B` on the Strix Halo over the network requesting from my Macbook started outputting endless `/` after a certain point, and a similar effect from `Gemma 4 31B` - and that seemed to be happening only on requests **from** the Macbook, not from any of the other machines in my network.
- Some harnesses have their own stability issues: OpenCode is more stable on the terminal version, but more complete on the desktop version; Pi is terminal-only, but doesn't provide local inference connection by default - I needed to install `@hypabolic/crossbar` in order to access the models over LM Studio in both same-machine and network cases, even if LM Studio is a standard available provider (though the listing of it there is misleading - it refers to LM Studio the cloud service, not LM Studio the desktop app).
